## 2. Render — API + worker

1. Render → **New → Blueprint** → this GitHub repo, branch `main`. It creates `saathmein-api` (web service, Singapore, Starter) and `saathmein-worker` (background worker).
2. Fill every `sync: false` value when asked (the group `saathmein-backend` is shared by both):
   - `MONGODB_URI` (Atlas production cluster, user with readWrite on `saathmein` only)
   - `REDIS_URL` (Upstash, `rediss://…`)
   - `TWO_FACTOR_ENCRYPTION_KEY`: 64 hex characters — run `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`
   - Firebase Admin (`FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL`, `FIREBASE_PRIVATE_KEY`)
   - Cloudinary, Razorpay **test** keys + webhook secret, `RESEND_API_KEY`, `EMAIL_FROM`, `SENTRY_DSN`
   - On the API only: `CORS_ORIGINS` (your Vercel domain(s), comma separated, no localhost), `SELLER_WEB_URL` (`https://<web-domain>/seller`), `APP_LINK_BASE_URL` (`https://<web-domain>`), `ANDROID_SHA256_CERT_FINGERPRINTS` (step 7.3), `EXPO_ACCESS_TOKEN` (optional)
   - On the worker: the same `CORS_ORIGINS`, `SELLER_WEB_URL`, `APP_LINK_BASE_URL`
   - JWT / deal-code secrets are generated by Render (`generateValue`). Do not change them later or every session and QR code becomes invalid.
3. The API refuses to start in production if anything important is missing or a placeholder (it prints which variable). Check **Logs** after the first deploy.
4. Check `https://<api>.onrender.com/api/health` → `"status":"ok"`, database `connected`, redis `connected`.
5. `autoDeploy` is off: deploy from Render → Manual Deploy after merging to `main`.

## 3. Vercel — web (dealer dashboard + admin console)

1. Vercel → New Project → this repo → **Root directory `web`**.
2. Environment variables (Production):
   - `NEXT_PUBLIC_API_URL=https://<api>.onrender.com/api`
   - `NEXT_PUBLIC_SOCKET_URL=https://<api>.onrender.com`
   - `NEXT_PUBLIC_SENTRY_DSN=<web DSN>`
3. Add your domain (e.g. `saathmein.in`). Share links `https://<domain>/g/<code>` and `/r/<code>` and `/.well-known/assetlinks.json` are proxied to the API by `next.config.mjs`.
4. Put the final web origin in Render `CORS_ORIGINS`, then redeploy the API.

## 4. Atlas production rules, backups, first data

- Cluster tier M10+ (backups and Vector Search for Days 15–20). Region: Mumbai (`ap-south-1`).
- **Backups:** enable Cloud Backup, daily snapshots kept 7 days + weekly kept 4 weeks; test one restore into a scratch cluster.
- **Network access:** Render does not have fixed outbound IPs on Starter → allow `0.0.0.0/0` **only together with** a long random DB password and a user limited to the `saathmein` database. (Upgrade to Render static outbound IPs later and lock the list.)
- Database users: one app user (`readWrite@saathmein`), one read-only user for you. No Atlas admin credentials in Render.
- First data (from your laptop, with the production `MONGODB_URI` in a temporary `backend/.env`):
  `npm run seed` → `npm run import:products` → `npm run search:indexes` → `npm run create-owner` → remove `OWNER_PASSWORD` from the file.

## 5. Razorpay (test mode)

- Dashboard (test mode) → Webhooks → `https://<api>.onrender.com/api/payments/webhook`, secret = `RAZORPAY_WEBHOOK_SECRET`, events: `payment.authorized`, `payment.captured`, `payment.failed`, `refund.processed`, `refund.failed`, `transfer.processed`, `transfer.failed` (the ones the API handles).

## 6. EAS production build (AAB 1.0.0)

1. `cd mobile && npx eas-cli@latest login && npx eas-cli init` (once; adds the project id).
2. EAS environment variables for the **production** environment (expo.dev → Project → Environment variables):
   - `EXPO_PUBLIC_API_URL=https://<api>.onrender.com/api`
   - `EXPO_PUBLIC_SOCKET_URL=https://<api>.onrender.com`
   - `EXPO_PUBLIC_APP_LINK_HOST=<web domain>` (no https://)
   - `EXPO_PUBLIC_WEB_URL=https://<web domain>`
   - `EXPO_PUBLIC_RAZORPAY_KEY_ID=<rzp_test_…>` (public key id only — never the secret)
   - `EXPO_PUBLIC_SENTRY_DSN=<mobile DSN>`
   - `GOOGLE_SERVICES_JSON` as a **file** variable (Firebase Android config)
   - Optional native crash symbols: `SENTRY_ORG`, `SENTRY_PROJECT`, and secret `SENTRY_AUTH_TOKEN`
3. Upload the FCM V1 service-account key in expo.dev → Credentials (push notifications).
4. `npx eas-cli build --profile production --platform android` → produces an **AAB**, version 1.0.0, version code auto-incremented by EAS.
5. Install the matching **preview** APK on a phone first if you want a quick check: `--profile preview`.

### 7.1 Store listing text (English)

- **App name (30):** SaathMein: Buy Together
- **Short description (80):** Join buyers near you, let verified dealers bid, and save on bikes and phones.
- **Full description:**

  SaathMein lets people in the same city buy the same product together and save.

  How it works
  • Find a group for the product you want, or start one and invite friends.
  • Join by paying a small refundable token through Razorpay (UPI, cards, net banking).
  • When the group is full, verified local dealers bid in a live auction. The lowest all-inclusive price wins.
  • Everyone in the group gets a deal code and buys from the winning dealer at that price.
  • If the group does not fill or no deal happens, your token is refunded automatically.

  Why SaathMein
  • Real dealer prices, compared live — no hidden charges in the final bid.
  • Verified dealers with KYC, ratings and reviews.
  • Your phone number stays private; group members see first names only.
  • Group chat, live member counter and price drops as they happen.
  • English, Hindi and Marathi.

  Launching in Pune with two-wheelers and mobile phones.

- **Category:** Shopping. **Contact email:** your support email. **Website:** your web domain.
- Hindi and Marathi listings: add after the English one is approved (the app itself is already translated).

### 7.2 Data safety answers (check against the final privacy policy)

Data is encrypted in transit: **Yes**. Users can request deletion: **Yes** — in the app (Profile → Delete account) and via the support email.

| Data type | Collected | Shared | Purpose | Optional |
|---|---|---|---|---|
| Phone number | Yes | No | Account management (login OTP) | No |
| Name, profile photo | Yes | No | Account management, app functionality (first name shown in groups) | Photo optional |
| Approximate location | Yes (rounded ~100 m, once, to find the city) | No | App functionality | Yes |
| Purchase history (groups, tokens, purchases) | Yes | No | App functionality, account management | No |
| Payment info (card / UPI) | **No** — entered in Razorpay Checkout, never on our servers | — | — | — |
| Messages (group chat), photos (dispute evidence, avatar) | Yes | No | App functionality | Yes |
| App interactions (products viewed / interests) | Yes | No | Personalisation (home feed, demand) | No |
| Crash logs, diagnostics | Yes (Sentry) | No | Analytics / app stability | No |
| Device or other IDs | Yes (random install id for OTP limits, push token) | No | Fraud prevention, security; notifications | No |

Razorpay, Firebase, Cloudinary and Sentry act as **service providers** (processing on our behalf), which Google does not count as "sharing".

## 8. Switching Razorpay to live (only after legal OK and your instruction)

1. CA / lawyer confirm: token as part-payment, refund policy, back-out fee, grievance officer; legal pages updated and `isDraft: false`.
2. Razorpay account activated for live payments **and Route**.
3. Render: replace `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET` with live keys; create the **live-mode** webhook (same URL and events) and set its secret as `RAZORPAY_WEBHOOK_SECRET`. Redeploy API + worker.
4. EAS: `EXPO_PUBLIC_RAZORPAY_KEY_ID=rzp_live_…` → new production build (the key id is baked into the app).
5. Dealers: linked accounts must be re-created in live mode (Admin → Sellers → Retry payout setup for each).
6. Smoke test with a ₹1 test product / small real token → refund it from Admin → Payments.

## 9. QA on 3 phones and the bug bash

Phones: one low-end (Android 8–10, 2–3 GB RAM, 360 dp wide), one mid-range (Android 12–13), one high-end (Android 14+). Use Hindi on one and Marathi on one.

Checklist per phone:
- [ ] Install from Play internal testing; cold start under ~2.5 s on the mid-range phone
- [ ] OTP login (real number), language, city by location and by hand, interests
- [ ] Home, search, browse filters, product page, dealer profile
- [ ] Start a group, share link opens the app (App Links), join with a test UPI token, live counter on another phone under 1 s
- [ ] Leave a group (refund), group chat (text, photo, poll, report), notifications arrive
- [ ] Auction: dealer bids on web, price drops live on the phone, winner, deal-code ticket, purchase confirmed by the dealer, review
- [ ] Wallet / referral, dispute with photos
- [ ] Airplane mode: offline card shows; home, my groups and the deal-code ticket still open; "Try again" works when back online
- [ ] Large font size (Settings → Display) and dark mode: no cut-off prices or deal codes
- [ ] Android back button everywhere, keyboard never covers inputs, 360 dp layouts

Bug bash (5 people, 60 minutes): two buyers, one leader, one dealer on the web, you in the admin console watching Live auctions, Payments and Alerts. Log every issue with phone model, steps and screenshot; P0 = money, login, crash, data shown to the wrong person.

## 10. Load test (staging or the production API before launch)

1. Create a **public** test group and copy its id from Admin → Groups.
2. From your laptop with the same `JWT_ACCESS_SECRET` and `REDIS_URL` as the API under test in `backend/.env`:
   `cd backend && npm run load-test -- --url https://<api> --group <groupId> --clients 500 --rate 50 --seconds 120`
3. Pass: ≥ 99% sockets connected, every update delivered, p95 latency < 1 s. Watch Admin → System health during the run.
4. Against production add `--i-know-this-is-production` (it only publishes counter updates; no data is written).

## 11. Monitoring after launch

- Sentry: alerts on new issues for the three projects (backend, web, mobile).
- Admin → Alerts: set your buyer-app phone in Settings → Alerts for push.
- Render: notify on deploy failure and on health-check failure.
- GitHub Actions CI runs lint + tests on every PR (`.github/workflows/ci.yml`).
